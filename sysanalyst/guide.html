The systems-analyst fundamentals — a study guide

Five domains, each with the core ideas and a quick 1-2-3 way to reason your way to the right answer under time pressure. Read it before a test, or after, to turn the "why" of each miss into something that sticks.

Jump to: APIs & REST · Protocols · Networking & OSI · Messaging & Queues · Databases & Data

1 · APIs & REST

REST is an architectural style, not a format. Its core constraints: resources named as nouns, a uniform interface of standard HTTP methods, and statelessness (each request self-contained).

Good vs. bad design — the tells

  • Good: GET /users/123/orders — nouns in the path, the verb is the HTTP method, hierarchy is obvious.
  • Bad: POST /getUserOrders?id=123 — a verb baked into the path (RPC-over-HTTP), and POST used for a read.
  • Good: a create returns 201 Created + a Location header; a missing resource returns 404.
  • Bad: returning 200 OK with {"error": …} — the status line lies to clients, proxies and caches.

Methods & semantics

  • Safe (no state change): GET, HEAD. Idempotent (repeat = same end state): GET, PUT, DELETE. Not idempotent: POST.
  • PUT replaces the whole resource; PATCH applies a partial update.
  • Status families: 2xx success · 3xx redirect · 4xx client error (401 = authenticate, 403 = forbidden, 404 = missing, 409 = conflict, 422 = valid-but-unprocessable, 429 = rate-limited) · 5xx server error (502/504 = bad/timed-out upstream).

Robustness

  • Idempotency keys let a retried POST (e.g. a payment) return the first result instead of double-charging.
  • Versioning: additive/optional changes are safe; renames, removals and type changes are breaking → new version (e.g. /v1/).
  • Pagination: prefer cursor/keyset over offset for large, changing lists. Auth: short-lived tokens in the Authorization header, never in the URL.

1-2-3: (1) Is the URL a noun and the action the HTTP method? (2) Does the status code match the real outcome? (3) If I retry this call, is the end state the same?

2 · Protocols

Protocol/styleShapeBest for
REST/JSONResources over HTTP, statelessPublic, cache-friendly, browser/mobile CRUD
SOAP/XMLStrict Envelope + WSDL, WS-*Formal enterprise/finance contracts, message-level security
gRPCProtobuf over HTTP/2, .proto contractFast, strongly-typed internal service-to-service calls; streaming
GraphQLClient selects fields; one endpointAvoiding over-/under-fetching across varied clients
WebSockets / SSEPersistent connection; pushLive updates — full-duplex (WS) or one-way server push (SSE)
  • SOAP = a protocol (always XML, WSDL contract, WS-Security signs/encrypts the message itself). REST = a style (format-agnostic, usually JSON).
  • gRPC gains bidirectional streaming and compact binary payloads from HTTP/2 + Protobuf — but browsers need gRPC-Web + a proxy.
  • GraphQL trades easy HTTP caching (one POST endpoint) and risks the N+1 resolver problem (fixed with batching/DataLoader).

1-2-3: (1) Public/browser + simple CRUD → REST. (2) Internal, high-volume, typed → gRPC. (3) Live push → WebSockets/SSE; strict XML partner contract → SOAP.

3 · Networking & the OSI model

Seven layers, top to bottom — mnemonic “All People Seem To Need Data Processing”:

  1. 7 Application — HTTP, DNS, SMTP, FTP (what apps speak)
  2. 6 Presentation — data format, translation, encryption/compression
  3. 5 Session — set up / maintain / tear down conversations
  4. 4 Transport — TCP/UDP, ports, segments (host-to-host delivery)
  5. 3 Network — IP, routers, packets (routing between networks)
  6. 2 Data Link — MAC, switches, frames (the local link)
  7. 1 Physical — bits on wire/radio
  • Router = L3 (routes by IP). Switch = L2 (forwards by MAC). L4 vs L7 load balancer = routes by IP/port vs by URL/headers.
  • TCP: reliable, ordered, connection (SYN → SYN-ACK → ACK), retransmits. UDP: connectionless, best-effort — good for live media. QUIC/HTTP-3: reliable multiplexed streams over UDP.
  • DNS maps names → IPs (A = IPv4, AAAA = IPv6, CNAME = alias, MX = mail); changes are gated by TTL caching. HTTPS = HTTP over TLS (encryption in transit + certificate auth; mTLS authenticates both sides).

1-2-3: (1) What does the device/protocol do? (2) Map that job to its layer. (3) If it's addressing → IP is L3, ports are L4; if it's the data's format/encryption → L6.

4 · Messaging & Queues (RabbitMQ)

In RabbitMQ a producer publishes to an exchange; bindings route to queues; a consumer reads and acks. Pick the exchange by how it chooses recipients:

  • Fanout → every bound queue (broadcast / pub-sub). Direct → exact routing-key match. Topic → pattern match (* = one word, # = zero-or-more). Headers → by header attributes.
  • Ack confirms processing so the broker drops the message; no ack (on crash) → redelivery. Prefetch (QoS) caps unacked messages per consumer for fair dispatch.
  • TTL + dead-letter exchange → expired/rejected messages go to a DLQ; cap retries so a poison message doesn't loop forever. Durable queue + persistent message survive a restart.

Delivery guarantees

  • At-most-once — may lose, never duplicates. At-least-once — may duplicate → consumers must be idempotent. Exactly-once — hardest; usually faked with at-least-once + dedup/idempotency.
  • RabbitMQ = route-and-remove broker. Kafka = retained, replayable, partitioned log (order within a partition; consumer groups share partitions).

1-2-3: (1) Who should receive it? → exchange type. (2) Can it be delivered twice? → make the consumer idempotent. (3) What happens on failure? → retries + DLQ.

5 · Databases & Data

  • SQL for structured, related data with transactions/joins. NoSQL by pattern: key-value (cache/session), document (flexible shape), wide-column (huge write scale), search (full-text).
  • Normalization stores each fact once (1NF atomic cells · 2NF no partial-key deps · 3NF no transitive deps) to avoid update anomalies. Denormalize deliberately (materialized views / read models) when reads dominate.
  • Indexes (default B-tree: equality + ranges) speed reads but cost writes; a composite index helps a leftmost prefix; a covering index answers a query without touching the table.

Transactions & scale

  • ACID: Atomicity · Consistency · Isolation · Durability. Isolation levels block anomalies: Read Uncommitted (dirty reads) → Read Committed (stops dirty) → Repeatable Read (stops non-repeatable) → Serializable (stops phantoms too). Stricter = safer but less concurrency.
  • Deadlock = a cycle of waits (DB aborts a victim). Optimistic concurrency checks a version at commit and retries.
  • CAP: under a partition, choose Consistency or Availability. Scale reads with replicas (watch lag → eventual consistency); scale writes/storage with sharding.

1-2-3: (1) What's the access pattern? → picks SQL vs which NoSQL. (2) Which anomaly must I prevent? → picks the isolation level. (3) Am I scaling reads or writes? → replicas vs sharding.
